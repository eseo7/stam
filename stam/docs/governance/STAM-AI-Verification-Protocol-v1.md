# STAM AI 검증 프로토콜 v1

> 이 문서는 STAM AI 기반 구현/검증 작업의 공식 운영 기준이다.  
> L3 이상 작업은 이 프로토콜을 반드시 준수한다.

---

## 1. 목적

STAM에서 AI를 활용한 구현 작업이 증가함에 따라, 결과물의 품질과 안전성을 일관되게 보장하기 위한 검증 체계가 필요하다.

이 프로토콜은 다음을 목적으로 한다.

- AI 기반 구현 결과의 객관적 검증
- 구현과 검사 역할 분리
- 사전 완료 조건(Acceptance Criteria) 기반 판정
- 문서 / 소스 / Preview 간 정합성 확보
- 회귀, 권한, 데이터 위험 방지

---

## 2. 핵심 원칙

### 2.1 기준 선작성 원칙

구현을 시작하기 전에 Acceptance Criteria를 먼저 작성하고 확정한다.  
구현 중 또는 완료 후에 기준을 추가·변경하지 않는다.

### 2.2 구현자와 검사자 분리

같은 세션이 구현과 검사를 동시에 수행하지 않는다.  
독립 검사는 별도 검사 세션에서 수행한다.

### 2.3 검사와 수정 분리

독립 검사자는 원칙적으로 대상 소스를 직접 수정하지 않는다.  
검사 결과를 문서로 남기고, 수정은 구현 담당자가 단독으로 수행한다.

### 2.4 단일 수정자 원칙

수정은 단일 구현 세션에서 순차적으로 진행한다.  
여러 세션이 동시에 같은 파일을 수정하지 않는다.

### 2.5 읽기 전용 검사 병렬화

읽기 전용 검사(문서 확인, 코드 리뷰, 정합성 검사)는 필요 시 병렬로 진행할 수 있다.  
파일을 수정하는 작업은 단일 수정자 원칙을 따른다.

### 2.6 증거 기반 판정

"PASS로 추정한다"는 허용하지 않는다.  
각 Acceptance Criteria에 대해 실제 확인 근거를 남긴다.

### 2.7 최신 Head SHA 검증

검사는 항상 최신 Head SHA 기준으로 수행한다.  
재검사 시 이전 검사 결과를 그대로 이월하지 않는다.

## 3. 적용 범위

이 프로토콜은 다음 영역의 STAM 작업에 적용한다.

| 영역 | 설명 |
|------|------|
| 문서 | 거버넌스 문서, 가이드, 계약 문서, 설계 문서 |
| UI | 제품 화면, Preview, 화면 컴포넌트 조립 |
| 공통 컴포넌트 | CSS, JS, DOM 패턴, 토큰 |
| 제품 기능 | 저장, 조회, 삭제, 필터, 검색 |
| 인증 | Firebase Auth, 로그인/로그아웃, 세션 |
| 권한 | 프로젝트 멤버, 역할, 접근 제어 |
| DB | Firestore 데이터 모델, CRUD |
| Firebase Rules | Firestore Rules, Storage Rules |
| 배포 | Firebase Hosting, GitHub Actions |

## 4. 작업 등급

모든 STAM 작업은 아래 4등급 중 하나로 분류한다.

| 등급 | 명칭 | 설명 |
|------|------|------|
| L1 | 경미 | 텍스트 수정, 오타 수정, 문서 링크 추가 |
| L2 | 일반 | 단일 화면 UI 조정, 단순 기능 추가 |
| L3 | 중요 | 공통 컴포넌트, 복수 화면 영향, 권한/데이터 변경 |
| L4 | 핵심 | 인증, Rules, 전역 CSS/JS, DB 스키마, 배포 설정 |

### 등급별 예시

| 등급 | 예시 |
|------|------|
| L1 | 문서 링크 추가, 버튼 텍스트 변경, 오타 수정 |
| L2 | 단일 제품 화면 신규 생성, 목록 필터 추가 |
| L3 | 공통 Picker, 공통 Dialog, 공통 Alert, 공통 Empty State, Firestore CRUD 추가 |
| L4 | Firebase Auth 변경, Firestore Rules 수정, 전역 CSS 토큰 변경, App Shell 수정 |

### 등급별 필수 검증

| 등급 | Acceptance Criteria | 독립 검사 | Smoke QA | Handoff |
|------|---------------------|-----------|----------|---------|
| L1 | PR 체크리스트 수준 | 선택 | 선택 | 불필요 |
| L2 | 템플릿 작성 | 권장 | 권장 | 선택 |
| L3 | 템플릿 작성 필수 | 필수 | 필수 | 필수 |
| L4 | 템플릿 작성 필수 | 필수 | 필수 | 필수 |

### L3 이상 기본 적용 대상

다음 작업은 별도 지정이 없어도 기본 L3 이상으로 처리한다.

- 공통 Picker
- 공통 Dialog
- 공통 Alert
- 공통 Empty State
- 인증 (Firebase Auth)
- 권한 (프로젝트 멤버, 역할)
- Firestore 데이터
- Firebase Rules
- 전역 CSS (stam.tokens.css, stam.components.css, stam.shell.css)
- 공통 Store / 상태 관리
- App Shell

## 5. 역할 정의

| 역할 | 책임 |
|------|------|
| **기준 작성자** | 작업 시작 전 Acceptance Criteria를 작성하고 확정한다. 작업 중 기준을 무단 변경하지 않는다. |
| **구현 담당자** | 확정된 Acceptance Criteria 범위 내에서 구현한다. 자체 테스트 후 독립 검사를 요청한다. |
| **독립 검사자** | 별도 검사 세션에서 Acceptance Criteria를 기준으로 판정한다. 대상 소스를 직접 수정하지 않는다. |
| **최종 게이트 담당자** | 독립 검사 결과와 Smoke QA를 검토하고 PR Ready / Merge 여부를 결정한다. |

## 6. 표준 절차

아래 흐름이 STAM AI 검증 공식 절차다.

```
1.  작업 목표 확정
2.  Acceptance Criteria 작성        ← 기준 선작성
3.  허용/금지 범위 고정
4.  구현
5.  구현자 자체 테스트
6.  Preview 생성
7.  독립 검사                        ← 별도 검사 세션
8.  문제 목록 작성
9.  순차 보정                        ← 단일 구현 세션
10. 독립 재검사                      ← 최신 Head SHA 기준
11. Browser Smoke QA
12. Ready 전환
13. Merge
14. 배포 후 확인
15. Handoff 기록
```

## 7. Acceptance Criteria 작성 규칙

### 7.1 추상적 기준 금지

다음과 같은 추상적 기준은 판정이 불가능하므로 사용하지 않는다.

```
❌ 적절히 구현한다
❌ 자연스럽게 표시한다
❌ 오류 처리가 잘 되어 있다
❌ 공통화한다
❌ 반응형을 고려한다
```

### 7.2 판정 가능한 기준 예시

```
✅ AC-FN-001: Picker 클릭 시 옵션 목록이 400ms 이내에 열린다
✅ AC-UI-001: 선택된 항목에 체크 아이콘이 표시된다
✅ AC-RS-001: 375px 뷰포트에서 Picker가 화면 너비를 초과하지 않는다
✅ AC-RG-001: 기존 Dialog 동작에 변화가 없다
✅ AC-AU-001: 비로그인 상태에서 Picker 접근 시 로그인 페이지로 이동한다
```

## 9. 독립 검사 규칙

독립 검사자는 다음을 반드시 준수한다.

1. 직접 수정하지 않는다.
2. 확인하지 않은 항목을 PASS로 추정하지 않는다.
3. 검사 전 최신 Head SHA를 확인한다.
4. Acceptance Criteria별로 개별 판정한다.
5. 재현 방법과 판정 근거를 문서에 남긴다.
6. 재검사 시 이전 PASS 결과를 자동 이월하지 않는다.

## 10. 판정 상태 정의

| 상태 | 정의 |
|------|------|
| **PASS** | 해당 Acceptance Criteria를 실제로 확인했으며, 기준을 완전히 충족한다. |
| **PASS WITH FOLLOW-UP** | 현재 기준은 충족하나, 후속 작업이 필요한 경미한 사항이 있다. 후속 작업 내용을 명시한다. |
| **FAIL** | 해당 Acceptance Criteria를 충족하지 못한다. 재현 방법과 심각도를 명시한다. |
| **BLOCKED** | 환경 문제, 접근 권한 부재, 의존 작업 미완료 등으로 검사를 수행할 수 없다. 차단 원인을 명시한다. |

### 중요: PASS WITH FOLLOW-UP 불가 항목

다음 항목에서 문제가 발견되면 PASS WITH FOLLOW-UP으로 처리할 수 없다. 반드시 FAIL 처리한다.

- 권한 오류
- 인증 오류
- 데이터 손상 또는 데이터 유실
- Firebase Rules 위반

## 11. 도구 독립 원칙

이 프로토콜은 특정 AI 도구(Cursor, Claude Code, Codex 등)의 명령어나 기능에 종속되지 않는다.

공식 개념은 다음 중심으로 정의한다.

| 개념 | 설명 |
|------|------|
| 구현 세션 | 소스 코드를 변경하는 단일 작업 세션 |
| 독립 검사 세션 | 구현과 분리된, 소스를 수정하지 않는 검사 전용 세션 |
| 읽기 전용 병렬 검사 | 파일을 수정하지 않는 검사를 동시에 여러 검사자가 수행하는 방식 |
| 단일 수정 담당자 | 한 번의 작업 사이클에서 소스를 수정하는 역할을 하나의 구현 세션으로 고정 |
